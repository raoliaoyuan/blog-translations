# 术语表 — 深度拆解 AWS 架构和内部计费机制

本表覆盖三篇连载中出现的专业术语，按主题分组。"出处"标明术语首次或核心出现的篇章。

## 核心机制

| 中文 | English | 出处 | 简释 |
|---|---|---|---|
| 归属收入 / 影子收入 / 关联归属收入 | Attributed Revenue | 1, 2, 3 | 内部财务系统中按"谁驱动了消费"重新归因的收入信号。AWS 在 Partner Central 已经把这一概念产品化（Partner Revenue Measurement），但 AWS 内部 PaaS / IaaS 团队之间是否使用同一字段名、比例、利润池，未找到公开来源支持 |
| 内部转移定价 | Transfer Pricing | 1, 2 | 在归因的基础上把底层资源成本、毛利或经营贡献按规则分摊给上层服务团队的财务接口。AWS 内部具体规则未公开 |
| 成本分摊标签 | Cost Allocation Tags | 1 | AWS 给客户的官方工具，按业务维度（cost center、owner 等）重新组织账单。客户可见的成本分摊机制 |
| 成本和用量报告 | Cost and Usage Report (CUR) | 1 | AWS 账单的最细粒度数据导出，`lineItem/ProductCode` 等字段是外部账单归属的基本维度 |
| 计费导体 | AWS Billing Conductor | 1 | 客户侧的 showback / chargeback 工具，是 AWS 对"同一份底层 usage 可按多种口径重新计价"思想的产品化 |
| 合作伙伴归因收入 | Partner Revenue Measurement (PRM) | 1, 3 | AWS 用 Resource Tagging、User Agent String、AWS Marketplace Metering 度量 partner solutions 驱动的 AWS consumption。Tier 1 公开机制 |
| 微软合作伙伴归因消费收入 | Partner Reported Azure Consumed Revenue (PRACR) | 3 | Microsoft 用来对齐 field incentive 与最终客户 Azure 消费的机制 |
| 微软消费收入指标 | Azure Consumed Revenue (ACR) | 3 | 客户实际消费 Azure 的货币价值 = 计量资源数量 × 单位价格。注意：Azure Container Registry 同样缩写为 ACR，二者不是一回事 |

## 组织设计

| 中文 | English | 出处 | 简释 |
|---|---|---|---|
| 二披萨团队 | Two-Pizza Team | 2 | 团队小到两张披萨可以喂饱（典型 < 10 人）；强调自治、单线程聚焦和端到端责任 |
| 单线程领导者 | Single-Threaded Leader (STL) | 2 | 对一个结果有单一聚焦和完整决策权的负责人，目的是减少传统矩阵组织的责任扩散 |
| API 强制令 | Bezos 2002 API Mandate | 2 | 2002 年前后 Bezos 要求所有团队必须通过服务接口暴露能力。Amazon 官方未公开原 memo，Steve Yegge 2011 年实名转述为主要二手来源 |
| 服务接口 | Service Interface | 2 | API Mandate 的具体形态：所有跨团队协作必须通过可外部化的接口发生 |

## 工作流与文化

| 中文 | English | 出处 | 简释 |
|---|---|---|---|
| 逆向工作法 | Working Backwards | 2 | Amazon 产品立项方法：从客户出发倒推到最小技术要求 |
| 新闻稿 + 常见问题 | PR-FAQ (Press Release + FAQ) | 2 | Working Backwards 的具体仪式：先写发布时的新闻稿和 FAQ，再讨论实现 |
| 领导力准则 | Leadership Principles (LP) | 2 | Amazon 的 14 条文化原则。本系列重点引用 Customer Obsession、Ownership、Frugality、Insist on the Highest Standards |
| 客户至上 | Customer Obsession | 2 | LP 之一：领导者从客户出发倒推工作 |
| 主人翁意识 | Ownership | 2 | LP 之一：长期思考，代表整个公司而不仅是自己团队 |
| 勤俭节约 | Frugality | 2 | LP 之一：用更少完成更多；约束孕育出机敏（resourcefulness）、自给自足和发明 |
| 最高标准 | Insist on the Highest Standards | 2 | LP 之一：持续提高标准，缺陷不被传递下去 |
| 输入指标 | Input Metrics | 2 | 团队可控动作的度量（API 可用性、单位成本等），区别于滞后的输出指标 |
| 输出指标 | Output Metrics | 2 | 收入、利润等结果型指标 |
| 代理指标 | Proxies | 2 | Bezos 2016 致股东信中提醒警惕的概念：流程本应为结果服务，复杂组织里容易变成目标本身 |
| 不同意但执行 | Disagree and Commit | 2 | LP 之一 / 决策原则：有义务提出不同意见，决定一旦作出就完整投入执行 |
| 周业务回顾 | WBR (Weekly Business Review) | 2 | Amazon 团队跟踪输入指标的会议机制 |
| 第一天 | Day 1 | 2 | Bezos 反复强调的公司心态：保持创业期的客户至上、警惕代理指标、拥抱外部趋势、高速度决策 |

## 服务与产品

| 中文 | English | 出处 | 简释 |
|---|---|---|---|
| 弹性 Kubernetes 服务 | Amazon EKS (Elastic Kubernetes Service) | 1 | AWS 的托管 Kubernetes，控制平面 $0.10/h（标准版），节点资源按 EC2/EBS/网络单独计费 |
| 弹性计算云 | Amazon EC2 (Elastic Compute Cloud) | 1 | AWS 的虚拟机服务，是本系列讨论的 IaaS 基础 |
| 弹性块存储 | Amazon EBS (Elastic Block Store) | 1 | EC2 的块存储 |
| 节俭计划 | Savings Plans (Compute) | 1 | 跨 EC2、Lambda、Fargate 自动套用的承诺折扣，验证了 AWS 把外部产品入口和内部 compute 经济性分开处理的设计 |
| 预留实例 | Reserved Instances (RI) | 1 | EC2 的长期承诺折扣 |
| 启动类型 | ECS Launch Type (EC2 / Fargate / External / ECS Managed Instances) | 1 | ECS 的基础设施兼容性维度 |
| Lambda | AWS Lambda | 1 | AWS 事件驱动 serverless 服务。底层用 Firecracker microVM 跑在 EC2 之上 |
| 轻量虚拟机监控器 | Firecracker (Virtual Machine Monitor, VMM) | 1 | AWS 自研 microVM，支撑 Lambda 和 Fargate |
| 弹性文件系统 | Amazon EFS (Elastic File System) | 2 | AWS 的托管 NFS 服务。2015-04 公布，2016-06 GA，从公布到 GA 约 14 个月 |
| 模型托管入口 | Amazon Bedrock | 3 | AWS 在模型调用层的托管入口。按 token / batch / provisioned throughput 等维度计费 |
| 训练加速器 | AWS Trainium / Inferentia | 3 | AWS 自研的训练 / 推理加速器，与 NVIDIA GPU 实例形成内部容量替代关系 |
| 数据传输 | Data Transfer (DTO / DTAZ / DTIR) | 3 | AWS 数据传输收费的三类：出互联网（DTO）、跨可用区（DTAZ）、跨 Region（DTIR） |
| 云监控 | Amazon CloudWatch | 3 | AWS 的可观测性服务，定价随日志摄入（ingest）和指标量增长 |
| 容器编排 | Amazon ECS / EKS / Fargate | 1 | ECS / EKS 是编排层，Fargate 是承载 compute 的容器原生服务 |
