## 第一部分：LLM 基础

### Q1. 基础模型（base model）与指令调优模型（instruction-tuned model）的区别

- 基础模型只在大规模语料上做下一 token 预测训练，会续写但不会"听话"。
- 指令调优模型在此基础上用人工整理的指令-回答对继续微调，常见手段是 RLHF 或 RLAIF（基于 AI 反馈的强化学习）。
- 真正进入产品的几乎都是指令调优版本，除非你要从零做特定领域微调。

### Q2. transformer 中的注意力（attention）机制为什么对 LLM 至关重要

- 每个 token 通过 Query 与 Key 的点积得到对其他所有 token 的权重，再对 Value 做加权求和。
- 解决了 RNN 难以高效捕捉远距离依赖的问题。
- 自注意力是 LLM 能跨数千 token 做指代消解、追踪上下文、做多步推理的核心。

### Q3. 上下文窗口（context window）大有什么实际代价

- 上下文窗口是单次前向传播能处理的 token 上限。
- 注意力的复杂度是 O(n²)，显存与算力随长度平方膨胀。
- 实际上还有"中间迷失"（lost in the middle）问题：上下文中段位置的信息更容易被忽视。

### Q4. 温度（temperature）对生成的影响

- 温度是 logits 在 softmax 之前的缩放系数。
- 温度为 0 时取最高概率 token，等价于贪心解码（greedy）；温度大于 1 时分布更平、输出更随机。
- 事实性任务用 0.0–0.3；需要发散创意的任务用 0.7–1.0。

### Q5. top-k 与 top-p（nucleus）采样的区别

- top-k 只在概率最高的 k 个 token 里采样。
- top-p 在累计概率超过 p 的最小 token 集合里采样，集合大小会随分布的熵自适应。
- top-p 通常更稳：低熵时只考虑少数候选，高熵时放宽，输出更连贯也更贴合上下文。

## 第二部分：检索增强生成（Retrieval-Augmented Generation, RAG）

### Q6. RAG 解决什么问题，核心组件是哪些

- LLM 有知识截止日期且容易在具体事实上幻觉。
- RAG 用检索来的文档把生成"锚定"住，把 LLM 的语言能力与实时或专属知识结合起来。
- 四大组件：摄取管线（切块 + 嵌入）→ 向量库 → 检索器（retriever）→ 生成器（LLM）。

### Q7. 切块（chunking）策略怎么选

- 固定长度切块（如 512 token + 50 token 重叠）最简单，但会切碎语义边界。
- 语义切块按嵌入相似度合并句子；分层切块在父子层级里检索小块、回填大块。
- 法律、合同、产品规格这类结构化文档，按章节标题做"结构感知"切块通常最稳。

### Q8. 混合检索（hybrid search）什么时候比纯向量好

- 混合检索 = 稠密向量 + 稀疏 BM25/TF-IDF + 互逆排名融合（Reciprocal Rank Fusion, RRF）或学习型重排。
- 纯向量擅长语义相似，但遇到产品代码、ID、人名这类需要精确字面命中的查询会失手。
- 企业搜索的查询分布几乎从来都是混合的，所以混合检索基本是默认选项。

### Q9. 重排器（reranker）和双编码器（bi-encoder）的差别

- 双编码器把 query 与 doc 分别编码成定长向量，再做点积——快但粗糙。
- 交叉编码器（cross-encoder）把 query 和 doc 拼接后做联合 cross-attention 打分——慢但准得多。
- 工程实践：双编码器从大语料里召回 top-K，交叉编码器在 top-K 上做精排。

### Q10. 怎么评估一条 RAG 管线

- 主流框架是 RAGAS，四个维度：忠实度（Faithfulness）、答案相关性（Answer Relevance）、上下文精准率（Context Precision）、上下文召回（Context Recall）。
- 生产里我（原作者）盯得最紧的是忠实度和上下文精准率，因为它们最能抓到幻觉和检索漂移。

### Q11. RAG 里的"中间迷失"

- Liu 等人 2023 的研究表明，LLM 更善于利用上下文头尾的信息，中段会被显著低估。
- 当你把多个 chunk 一股脑塞进 prompt 时，这个问题被放大。
- 缓解办法：用 reranker 把最相关 chunk 放最前；减少塞入数量；用边界 token 做明显标记。

### Q12. 朴素（naive）RAG 在生产里常见的失效方式

- 切块粒度不对：太大稀释信号、太小丢失上下文。
- 嵌入模型与查询域不匹配（医学嵌入硬塞法律查询，等等）。
- 不做重排，仅靠余弦相似度——最像不等于最相关。
- 没有越界查询的 guardrail，上下文一无关 LLM 就开始编。
- 没有引用追踪，答案不可审计。每一项都得在生产里显式处理。

## 第三部分：提示工程

### Q13. 思维链（chain-of-thought, CoT）什么时候有用

- CoT 让模型先把推理步骤写出来，再给最终答案。
- 在算术、多步推理、需要中间逻辑可验证的任务上稳定带来增益。
- 在大模型（7B+ 参数）上效果最明显；简单分类、检索任务上只会徒增延迟。

### Q14. zero-shot、few-shot、fine-tune 的取舍

- zero-shot：只描述任务；few-shot：给 2–8 个示例；fine-tune：在任务数据集上调权重。
- 经验上，few-shot 能补上 zero-shot 到 fine-tune 之间约 70–80% 的差距。
- 想要稳定输出格式、专业词汇、亚 100ms 级延迟、或有 1000+ 高质量样本时，fine-tune 才值回工程开销。

### Q15. 提示注入（prompt injection）怎么防

- 提示注入是指用户输入里藏着试图覆盖系统提示的指令（"忽略此前所有指令……"）。
- 防御组合拳：用 XML 标签或特殊 token 把用户输入和系统指令清晰隔开；输入校验/清洗；上一道独立的 LLM 输入分类器；输出做白名单/格式校验。
- OWASP 把它列为 LLM 应用首位安全风险。

## 第四部分：多智能体系统

### Q16. 多智能体（multi-agent）LLM 系统什么时候用

- 多 agent 系统让多个有专门角色的 LLM agent（researcher、coder、reviewer 等）协作完成复杂任务。
- 适用场景：任务在单个上下文窗口里塞不下；可并行；需要专精分工与互相验证。
- 主流编排框架：CrewAI、LangGraph、AutoGen。

### Q17. ReAct 与 Plan-and-Execute 的差别

- ReAct（Reason + Act）把推理和工具调用交织在同一个循环里：思考 → 行动 → 观察 → 重复。简单，单步工具用足够好。
- Plan-and-Execute 把"先规划"和"再执行"分开：先让 planner 出完整计划，再交子 agent 执行各步。
- 长程任务用 Plan-and-Execute 更稳，目标不容易在迭代调用里被冲掉。

### Q18. 怎么避免 agent 陷入死循环

- 硬上限：迭代次数 / 工具调用次数。
- 加循环检测启发式：连续 N 次出现相同状态或动作序列就中断。
- 用一个 supervisor agent 监控子 agent 进度，必要时介入。
- 在任务分解的 prompt 里显式写出终止条件。
- 设置 token 与 API 调用的预算上限。

### Q19. LangGraph 里 agent 间怎么共享状态

- LangGraph 把 agent 工作流表达为有向图，状态是一个共享的 TypedDict 对象。
- 每个节点（agent 或工具）从中读、向其中写，conditional edge 根据状态值路由执行。
- 复杂多 agent 系统可以把子图隔离出独立 state schema，在图边界做消息传递，避免互相污染。

### Q20. agent 系统里的"记忆"分几种

- 上下文内记忆：当前会话/任务历史。
- 外部情景记忆（episodic）：过往交互存进向量库，按需检索。
- 语义记忆（semantic）：事实性知识库，常常就是一个 RAG 系统。
- 程序性记忆（procedural）：学到的工作流或工具使用模式，有时以微调权重形式存在。
- 真正影响性能的杠杆是：什么进上下文、什么留外部。

## 第五部分：微调与对齐

### Q21. 什么时候选 fine-tune，什么时候选 RAG

- RAG 适用：知识需要可更新、可审计、域特化，又不想动模型权重。
- fine-tune 适用：需要稳定的输出格式/风格；任务技能基础模型没有；延迟苛刻塞不下检索步骤；有 1000+ 高质量标注。
- 最常见的最优解是两者结合：fine-tune 控格式与风格，RAG 锚定事实。

### Q22. LoRA 为什么比 full fine-tune 更受欢迎

- LoRA（Low-Rank Adaptation）冻结预训练权重，在 transformer 每层注入低秩可训练矩阵。
- 可训练参数量大约缩到 full fine-tune 的万分之一，单卡就能微调 7B+ 模型。
- QLoRA 进一步把冻结权重 4-bit 量化，让单张 48GB 卡能调 65B。
- 大多数生产场景，LoRA / QLoRA 用一小部分成本拿到 90%+ 的 full fine-tune 效果。

### Q23. RLHF 已知的局限有哪些

- 人类反馈强化学习（Reinforcement Learning from Human Feedback, RLHF）训练一个奖励模型，再用 PPO 优化 LLM。它是目前对齐效果最强的方法。
- 局限：奖励 hacking（学会刷分而非真改进）；标注员之间方差与偏见；迭代慢成本高；KL 惩罚不够时分布会塌缩。
- DPO（Direct Preference Optimization, 直接偏好优化）作为更简洁的替代，省掉了显式 RL 这一段。

## 第六部分：LLM 评估与可观测性

### Q24. 生产里怎么衡量 LLM 输出质量

- 组合拳：自动化的"大模型当评委"（LLM-as-Judge）评分；任务专属指标（摘要看 ROUGE / BLEU、抽取看 F1、代码看 pass@k）；RAG 用 RAGAS；高风险场景上人工评估。
- 重点是看分布随时间的变化——分布突变常常先于用户投诉。

### Q25. LLM-as-Judge 的失效方式

- 位置偏置：在两两比较时倾向于选第一个。
- 自我增强偏置：同款模型评自己的输出会偏高。
- 长度偏置：不论质量，长输出更容易得高分。
- 缓解：随机化候选顺序、用多个评委做集成、控制输出长度。

### Q26. 生产用的 LLM 可观测性工具

- 常见组合：LangSmith（LangChain 系）、Phoenix（Arize）、Langfuse、PromptLayer。
- 至少要追踪：prompt 与 completion 内容、token 数、延迟、工具调用结果、检索分数、最终输出质量分。
- 报警放在：延迟尖峰、token 消耗异常、judge 分数下跌。

## 第七部分：架构与系统设计

### Q27. 给一万份文档的企业知识库设计生产级 RAG

- 摄取：用 LlamaParse / Unstructured.io 这类做结构感知解析；用 text-embedding-3-large 或微调过的 E5 做嵌入。
- 存储：按规模选 Pinecone / Weaviate / pgvector。
- 检索：BM25 + 稠密向量混合 + cross-encoder 重排。
- 生成：结构化输出带引用；用 RAGAS 做忠实度校验；上下文分低于阈值时明确回答"不知道"。
- 可观测性：每条 query 全链路追踪到 LangSmith；忠实度下跌触发告警。

### Q28. 多租户 RAG 怎么做数据隔离

- 在向量库这一层做命名空间或元数据过滤——Pinecone namespace、Weaviate tenant 隔离都是为此设计的。
- 查询时强制按 tenant_id 过滤；极敏感场景给每个租户开独立索引（更贵但零交叉风险）。
- API 层叠加 RBAC（基于角色的访问控制），代码里明确禁掉跨租户检索路径。

### Q29. 怎么压低生产 chatbot 的延迟

- 流式输出：第一时间往客户端推 token，而不是等整段。
- 模型分级：简单查询走小模型，复杂的再路由到大模型。
- 提示缓存：把系统提示前缀缓存起来（Anthropic 与 OpenAI 都支持）。
- 异步工具调用：互不依赖的工具并行跑。
- 量化推理：自托管时用 4-bit 或 8-bit 量化模型。

### Q30. LLM 应用里的 guardrails

- guardrails 是套在 LLM 调用前后的校验层，确保输入输出符合安全与合规要求。
- 输入侧：话题分类器、PII（个人身份信息）检测、注入检测。
- 输出侧：幻觉检测、格式校验、毒性过滤。
- 常用框架 NeMo Guardrails、Guardrails AI；在医疗、金融这类强监管行业属于必选项。

## 第八部分：自然语言到 SQL（NL-to-SQL）与结构化数据

### Q31. NL-to-SQL 系统的主要失效模式

- schema 歧义：同一概念在不同表里命名不一。
- 多跳 join 推理错。
- 幻觉出根本不存在的表名/列名。
- 聚合函数用错（该 SUM 用了 COUNT 之类）。
- 日期/时间运算错。
- 缓解：把 schema 上下文连同示例一起喂；针对目标 schema 做 few-shot 演示；加 SQL 校验层；用执行反馈让 LLM 自纠（执行报错回灌再生成）。

### Q32. schema 太大装不下怎么办

- 两阶段检索：先用 query 嵌入检索最相关的几张表，只把这些表的 DDL 与样本行喂给 LLM 写 SQL。
- Vanna.ai 就是这种模式。
- schema 极大时，可以单独训一个理解 schema 的子模块，用合成的 query-schema 对来训练。

## 第九部分：知识图谱与结构化检索

### Q33. 什么时候用知识图谱（knowledge graph）而不是向量库

- 实体之间的关系语义本身很重要时（"谁向谁汇报"这类查询）。
- 需要跨多个实体做多跳推理时。
- 需要精确、可审计的来源时。
- 微软的 GraphRAG 把图遍历与向量检索结合，在需要从多个实体综合信息的"社区级"问题上明显胜过 naive RAG。

### Q34. GraphRAG 与标准 RAG 的差别

- GraphRAG 在索引阶段从语料里抽出实体-关系图。
- 查询时检索的是相关的"图社区"（关联实体的簇），而不是单个 chunk，再把社区摘要作为上下文。
- 在"这个语料库的主要主题是什么"这种全局综合性问题上效果显著更好，代价是索引时间与复杂度更高。

## 第十部分：快问快答

### Q35. 语义搜索 vs 关键词搜索

- 语义搜索用稠密嵌入找概念相似；关键词搜索（BM25）匹配字面或词干重合。
- 同义词、改写表达靠语义；专有名词、精确 ID 靠关键词。

### Q36. 什么是 function calling

- LLM 不返回自然语言，而是返回一段结构化 JSON，明确说明该调用哪个函数、传哪些参数。
- 让工具使用变得可靠，是大多数 agent 框架的基础。

### Q37. 什么是宪法 AI（Constitutional AI, CAI）

- Anthropic 的对齐路径：让模型对照一组原则（"宪法"）自我批判并修订输出。
- 减少了对人工标注有害内容的依赖。

### Q38. 什么是推测式解码（speculative decoding）

- 用一个小的 draft 模型并行生成多个候选 token，再用大的 target 模型一次前向把它们一起验证掉。
- 长生成场景大约能拿到 2–3 倍加速。

### Q39. LangChain、LlamaIndex、LangGraph 的差别

- LangChain：通用 LLM 应用框架，集成最广。
- LlamaIndex：专注数据摄取、索引、RAG。
- LangGraph：低层级图执行引擎，适合需要严格控制 agent 状态与流程的有状态、多步工作流。

### Q40. 离线评估 vs 在线评估

- 离线：在固定 benchmark 数据集上评，快、可复现，但可能与生产分布不一致。
- 在线：抽样生产流量 + LLM-as-Judge 打分，反映真实用户行为，但迭代慢。
- 工程实践：维护一套离线回归测试套件 + 上线后持续监控在线指标。

## 笔者按

原作者强调的一句话很值得抄下来：**面试里真正区分人的不是"知道定义"，而是"能讲清取舍"。**为什么用混合检索而不是纯向量？什么时候 fine-tune 比 prompting 划算？为什么这个项目选 LangGraph 而不是 LangChain？答案后面如果能站着真实的生产经验，分量就很不一样。

这条复习清单放在 2026 年看，可以看出朴素 RAG 已经被默认成基线，面试官的探测点早就移到了 agent 记忆、GraphRAG、多模态管线这些方向。
