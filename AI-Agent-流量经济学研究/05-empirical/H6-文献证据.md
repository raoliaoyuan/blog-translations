# H6 文献证据：Anthropic cache_read 是否仍发送完整 prompt

> 结论：**判为情景 A**，证据等级 **L2**。截至 2026-06-27，公开文档与官方 SDK 源码支持的判断是：Anthropic prompt caching 命中 `cache_read` 时，客户端请求仍按 Messages API 的常规方式提交完整 prompt / history；缓存优化发生在服务端 prefill、计费与延迟层，不是客户端上行 HTTP body 字节削减。

## 1. Anthropic 官方文档证据

先区分一句关键事实：我没有找到 Anthropic 文档逐字写出“cache_read 命中时 HTTP request body must contain the full prompt”。但是，官方文档给出的 API 形态和缓存查找机制已经足以排除“只发 cache key”的协议。

第一，Messages API 是无状态接口。Anthropic 在 Messages API 指南中说明，多轮对话需要开发者把完整历史作为 `messages` 传入；原文要点是 “stateless” 且 “always send the full conversational history” [Anthropic Messages API guide](https://platform.claude.com/docs/en/build-with-claude/working-with-messages)。这不是 prompt caching 专属段落，但它定义了 `/v1/messages` 的基本请求语义：服务端不把上一次会话历史当作可被 `cache_read` 引用的会话状态。

第二，prompt caching 文档说自动缓存是在 request body 顶层增加 `cache_control`，显式缓存是在 content block 上放 `cache_control`；文档还写明 prompt caching references the entire prompt，即按 `tools`、`system`、`messages` 的顺序引用到 breakpoint 为止的完整前缀 [Anthropic Prompt Caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。这说明 `cache_control` 是 breakpoint marker，不是可替代 prompt 内容的句柄。

第三，缓存查找方法是 prefix hash。Anthropic “How automatic prefix checking works” 描述：cache write 只在 breakpoint 写入一个“prefix ending at that block”的 hash；每个请求中，系统会在 breakpoint 计算 prefix hash，若不命中再向前逐块 look back，最多 20 个位置 [Anthropic Prompt Caching: automatic prefix checking](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。同页还强调 cache hit 要求 prompt segments 100% identical [Anthropic Prompt Caching: cache storage and sharing](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。要在服务端计算这些位置的 prefix hash，服务端必须看见该请求中的 prefix 内容；公开文档没有给出“客户端提交 cache id，服务端跳过内容”的替代路径。

第四，usage 字段定义也支持这个解释。Anthropic 把 `cache_creation_input_tokens` 定义为写入缓存的 tokens，把 `cache_read_input_tokens` 定义为本请求从缓存取回的 tokens，把 `input_tokens` 定义为既未读缓存也未写缓存的 tokens，并给出 `total_input_tokens = cache_read_input_tokens + cache_creation_input_tokens + input_tokens` [Anthropic Prompt Caching: tracking cache performance](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。注意这里的 `input_tokens` “不是你发送的全部 input tokens”，而是计费/处理分类后的剩余部分。它证明 cache_read 改变 token 计量与 prefill 来源，但不等价于 wire bytes 变小。

第五，官方 cookbook 的请求构造方式很直接。示例先把《Pride and Prejudice》全文拼入 `messages[0].content`，第一次带 `cache_control` 写缓存；第二次 cache hit 标注为 “Same request again”，代码仍把同一个 `book_content` 拼进 `messages`，只是 usage 中 `cache_read_input_tokens` 变为 187361、`input_tokens` 变为 3 [Claude Cookbook: Prompt caching through the Claude API](https://platform.claude.com/cookbook/misc-prompt-caching)。这不是抓包测量，但它是官方示例层面的强信号：cache hit 的调用代码没有改成 cache key 或引用式请求。

因此，官方文档证据的边界是清楚的：它没有直接报告 HTTP 字节数，也没有给出 packet capture；但它把请求语义、缓存标记、prefix hash、usage 计量和示例代码连成同一套机制。若情景 B 成立，文档至少需要公开一种“历史内容引用”参数，或说明 cache hit 时可省略 prefix；目前未找到这种说明。

## 2. Anthropic 官方 SDK 源码证据

Python SDK 的 `messages.create` 直接调用 `self._post("/v1/messages", body=maybe_transform({...}))`，body 中包含 `max_tokens`、`messages`、`model`、`cache_control`、`system`、`tools` 等字段 [anthropic-sdk-python messages.py](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/resources/messages/messages.py)。这段实现没有根据缓存命中状态删除 `messages`、截断 `system`、替换成 cache id，或把历史内容改写成引用。`cache_control` 只是 body 中和 prompt 并列的参数。

类型定义进一步确认 marker 的语义。Python SDK 的 `TextBlockParam` 仍要求 `text`，只是可选附带 `cache_control`，注释为在该 content block 创建缓存 breakpoint [text_block_param.py](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/types/text_block_param.py)。`CacheControlEphemeralParam` 只有 `type: "ephemeral"` 和可选 `ttl`，没有 `cache_key`、`cache_id` 或 prefix 引用字段 [cache_control_ephemeral_param.py](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/types/cache_control_ephemeral_param.py)。因此官方 Python SDK 的答案是：带 `cache_control` 的消息仍作为完整 JSON body 发出，SDK 无“只发 cache key”的优化。

TypeScript SDK 同样如此。`messages.create` 里 `const { user_profile_id, ...body } = params`，随后 `this._client.post('/v1/messages', { body, ... })`；类型定义把 `messages` 标为 body param，并把顶层 `cache_control` 描述为自动把 marker 应用到最后一个可缓存 block [anthropic-sdk-typescript messages.ts](https://github.com/anthropics/anthropic-sdk-typescript/blob/main/src/resources/messages/messages.ts)。TS 版也没有 cache hit 分支或 body 字节削减逻辑。

这也回答了 API reference 中 `cache_control` marker 的工作机制：从官方生成的 SDK 类型看，`cache_control` 是请求体中的缓存断点控制项，作用是标记“到哪里可以写入或读取缓存”，而不是“从哪里读取一个外部缓存对象”。Python 与 TypeScript 两个官方 SDK 互相印证，降低了把某个语言客户端实现误读为偶然行为的风险。

## 3. 社区 benchmark 与 blog

指定检索 Simon Willison、Pamela Fox、a16z、Latent Space 以及 “Anthropic prompt caching bytes / request body / cache_read” 等组合后，未找到第三方公开文章做 Anthropic cache_read 的字节级或网络级抓包测量。找到的社区/学术材料主要测 cost、TTFT、策略差异。例如 2026 年 arXiv 论文《Don’t Break the Cache》评估 OpenAI、Anthropic、Google 的 prompt caching，在 500+ agent sessions 中测量成本和 TTFT，报告成本下降 41-80%、TTFT 改善 13-31%，但摘要没有报告客户端 HTTP body 字节或网络流量 [arXiv:2601.06007](https://arxiv.org/abs/2601.06007)。因此社区证据目前不能把 H6 升到 L1，只能作为“无人给出反例”的辅助事实。

## 4. 与 OpenAI 对比

OpenAI prompt caching 文档也采用 exact prefix / hash / cache lookup 叙述，并用 `cached_tokens` 表示多少 prompt tokens 命中缓存；文档没有把 prompt caching 描述成省略请求体历史的机制 [OpenAI Prompt Caching](https://developers.openai.com/api/docs/guides/prompt-caching)。同时，OpenAI 另有真正的省历史路径：Conversation state 文档说明 Responses API 是 stateful，能用 `conversation` 或 `previous_response_id` 串联上下文，让开发者不必每轮手工传入全部输入 [OpenAI Conversation State](https://developers.openai.com/api/docs/guides/conversation-state)。API reference 也定义了 `cached_tokens` usage，并出现 `previous_response_id` 字段 [OpenAI Responses API reference](https://developers.openai.com/api/reference/resources/responses/methods/create)。这构成有用反例：如果供应商提供“只发引用/增量”的协议，文档会明确暴露 state id；Anthropic prompt caching 没有等价字段。

## 5. H6 判定

情景 A（cache_read 仍需完整提交 prompt）证据强度：**强，L2**。依据是 Anthropic Messages API 无状态、prompt caching 的整段 prefix/hash/lookback 机制、usage 字段定义、官方 cookbook cache hit 请求仍构造完整内容，以及 Python/TypeScript 官方 SDK 100% 把 `messages/system/tools/cache_control` 序列化进 JSON body。

情景 B（cache_read 只发 cache key）证据强度：**未找到支持**。官方文档无 cache key 请求格式，SDK schema 无 cache id 字段，源码无按缓存命中裁剪 body 的逻辑；社区检索也未找到字节级实测反例。

综合判定：**H6 在文献证据下应判为情景 A，证据等级 L2**。更精确地说：Anthropic prompt caching 可以减少计费 input tokens、服务端 prefill 计算和 TTFT，但在现有 `/v1/messages` API 与官方 SDK 语义下，不能视为减少客户端到服务端 HTTP request body 字节。若要升到 L1，仍需抓包；但用户已决定跳过实测时，L2 足以支撑报告结论。

本判定的保守性在于：它不声称观察到了真实网络包，只声称公开协议和官方客户端没有省字节路径。

## 可挂载到 Part 5A 的修订版表述

**字节层（L2 文献证据）**：Anthropic prompt caching 的 `cache_read_input_tokens` 表示服务端从缓存复用的 prefix tokens，不表示客户端省略了这些 tokens 的 HTTP body 传输。Anthropic Messages API 是无状态接口，官方 prompt caching 文档采用完整 prefix hash/lookback 查找，官方 Python/TypeScript SDK 也将 `messages`、`system`、`tools` 与 `cache_control` 一起作为完整 JSON body 提交。因此，cache_read 优化的是服务端 prefill、计费和延迟；对客户端→服务端上行字节，当前公开证据支持“未削减”判定，证据等级 L2。
