# 第五部分 A 节　本地 Claude Code 会话实测

> 内部研究报告 · 草稿 v0.1 · 证据强度：**已实测（低样本）**

## 5A.1 数据来源与样本

- **数据集**：单一用户（本报告作者）2025–2026 年使用 Claude Code 客户端的完整会话日志
- **路径**：`~/.claude/projects/<project-slug>/<session-uuid>.jsonl`
- **总规模**：1,533 个会话文件，48,633 次 assistant 调用记录，385 MB 原始 JSONL
- **覆盖时间**：约 18 个月，跨 15 个项目目录
- **覆盖模型**：claude-opus-4-7、claude-opus-4-8、claude-sonnet-4-6、claude-haiku-4-5、claude-fable-5
- **采集方法**：Claude Code 客户端本地自动记录，无需额外抓包
- **复现脚本**：[`scan-sessions.py`](scan-sessions.py)
- **完整结果**：[`scan-summary.md`](scan-summary.md)

**样本性质说明**：单用户、单客户端、偏向编码型 Agent workload；不代表对话型、客服型、RAG 型等其他 Agent。结论**仅可作为"编码型 Agent 在重度用户场景下的下限锚点"**。

## 5A.2 字段口径

Claude API 返回的 `usage` 字段含四个 token 维度（[Anthropic API 文档](https://docs.anthropic.com/en/api/messages)）：

| 字段 | 含义 | 计费 | 是否计入上行 usage token |
|---|---|---|---|
| `input_tokens` | 本轮新增、未命中缓存的输入 | 1× | 是 |
| `cache_creation_input_tokens` | 本轮写入 cache 的输入 | 1.25× | 是 |
| `cache_read_input_tokens` | 命中 cache 的输入 | 0.1× | 是（作为 usage token 计） |
| `output_tokens` | 模型生成 | 5× | 否（下行 usage token） |

**关键口径限定**：cache_read 字段计入服务端报告的 usage token；**其字节是否完整走客户端→服务端 HTTP 请求体**已通过文献证据法（[H6-文献证据.md](H6-文献证据.md)）确证为 **L2 是**——Anthropic prompt caching 服务端通过 cumulative prefix hashing 识别匹配，要求客户端完整提交内容。**仍未实测的是 token→网络字节的编码层放大系数**（JSON / SSE / base64 / HTTP2 / TLS），这部分留为 L4。

本报告采用：
- **上行 usage token = input + cache_creation + cache_read**（这是 API 计量，**不等于网络字节**）
- **下行 usage token = output**

## 5A.3 总体分布

### 5A.3.1 全样本

| 指标 | 数值 |
|---|---|
| assistant 调用数 | 48,633 |
| 上行 **usage token** 总计 | 6,543,776,386 |
| 下行 **usage token** 总计 | 40,394,466 |
| **总体 上行/下行 usage token 比** | **162.0 : 1** |

**口径再次强调**：这是 Anthropic API 报告的 usage token 比例，**不是网络字节比**。网络字节比需要在客户端做 HTTP body 抓包才能确定，本研究尚未做。下文凡涉及"流量""字节""带宽"的推算，都建立在 token≈字节 的**未实测假设**（L4）之上。

### 5A.3.2 上行 token 的组成

| 组成 | token | 占上行比例 |
|---|---|---|
| 新增（未缓存）输入 | 18,925,144 | **0.3%** |
| 缓存写入 | 238,354,762 | 3.6% |
| 缓存读取 | 6,286,496,480 | **96.1%** |

**这一组成是本研究最关键的 usage token 层面发现**：

96.1% 的上行 usage token 计入"服务端报告的 prompt cache_read"。其含义需分两层看：

1. **计费层（L1 已实测）**：prompt caching 极大降低了用户的 token 计费成本（cache_read 单价仅 0.1×）。
2. **字节层（L2 文献证据已确证）**：cache_read 字段对应内容**仍需要**客户端通过 HTTP 请求体完整提交——服务端通过 cumulative prefix hashing 识别缓存匹配（[Anthropic Prompt Caching 文档](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching)），客户端 [SDK 源码](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/resources/messages/messages.py) 确认完整 JSON 序列化整个 messages / system / tools 数组无 cache 优化。因此 prompt caching **未削减客户端→服务端 HTTP 字节**，**只削减计费与服务端 prefill 计算成本**。详细证据链见 [H6-文献证据.md](H6-文献证据.md)。
3. **方向性洞察（L3）**：真正驱动 Agent 上行 token 的不是"用户输入"或"AI 输出"，而是**工具循环本身**——每读一个文件、跑一个 grep，整段对话历史在下一轮都要重新提交（**字节层已 L2 确证**）。
4. **协议生态（L2 修正）**：原稿"无主流厂商提供客户端缓存"表述过强。实际上：
   - **OpenAI** 通过 [`previous_response_id`（Responses API conversation state）](https://developers.openai.com/api/docs/guides/conversation-state) 提供服务端会话状态，客户端可省略历史重传——这是真正的字节削减协议
   - **Anthropic** 当前主要依靠 [prompt caching](https://platform.claude.com/docs/en/docs/build-with-claude/prompt-caching)（服务端 prefill + 计费优化），**架构上不削减客户端字节**
   - 因此 OpenAI 已有"字节削减路径"，Anthropic 当前没有等价协议

### 5A.3.3 单次调用上下行比例分位数

| 分位 | up/down 比例 |
|---|---|
| p10 | 61.5 |
| p25 | 135.6 |
| p50 | **386.6** |
| p75 | 5,055.6 |
| p90 | 24,470.0 |
| p95 | 38,268.0 |
| p99 | 71,149.0 |

中位数 386:1 比总体加权 162:1 高一倍多，说明**调用规模分布严重右偏**：少量"短输入大输出"调用（最初的提问与文档生成）拉低了加权均值，主体调用是"巨量上下文 + 几百 token 输出"。p99 的 71,000:1 对应的是工具循环里"读了大文件、模型只回一句 OK"或"只调用一个工具就停"的情况。

### 5A.3.4 按模型聚合

| 模型 | 调用数 | 上行 token | 下行 token | 比例 |
|---|---|---|---|---|
| claude-opus-4-8 | 25,843 | 3.83 B | 24.7 M | 154.9 |
| claude-opus-4-7 | 10,910 | 1.98 B | 11.7 M | 169.8 |
| claude-sonnet-4-6 | 7,780 | 257.8 M | 1.2 M | **214.8** |
| claude-fable-5 | 2,617 | 423.4 M | 2.6 M | 160.0 |
| claude-haiku-4-5 | 1,483 | 59.7 M | 0.21 M | **281.1** |

**观察**：小模型 / 副驾驶模型的比例更极端（Haiku 281:1，Sonnet 215:1）。原因可能是这些模型常被路由去做"短决策"调用——子任务分派、工具结果摘要、简单分类——回复短而上下文仍然要全送。这一现象支持一个假设：**Agent 架构里使用越多小模型做"流水线节点"，上行/下行不对称越极端**。该假设有待跨厂商样本验证。

### 5A.3.5 按项目类型聚合（top 5）

| 项目 | 调用数 | 比例 | 说明 |
|---|---|---|---|
| `subagents`（自动 Agent 路由） | 21,628 | 228.5 | 多 Agent 编排，长上下文+短回复 |
| `LocalFind`（编码项目） | 16,774 | 165.6 | 典型编码型 Agent，主导样本 |
| `Stock`（金融分析） | 1,993 | 112.2 | 偏对话与解释 |
| `Service-On-Service` | 1,575 | 148.9 | 工具密集型 |

**观察**：比例与 workload 类型强相关。多 Agent 编排（subagents）达 228:1；纯对话/写作场景仅 14:1。这给"按 workload 分类讨论流量结构"提供了实测支撑。

## 5A.4 从 token 比换算到字节比

本节区分两个独立问题：

### 5A.4.1 cache_read 字节是否仍传输（L2 已解决）

cache_read 内容**确实需要**客户端通过 HTTP body 完整提交——Anthropic 服务端通过 cumulative prefix hashing 识别缓存命中，没有 cache key 替代路径。详见 [H6-文献证据.md](H6-文献证据.md)。**这部分原作为开放假设 H6 留存，现已升级为 L2 文献证据确证。**

### 5A.4.2 token→网络字节的编码层放大系数（仍 L4 未实测）

token 比与网络字节比之间的换算受多层编码影响，**这部分未实测**：

- **上行（input → HTTP request body）**：JSON + UTF-8 + HTTP/2 + TLS。每 token 字节膨胀理论上在 3–5×（含 JSON 结构、字段名、消息分隔）；多模态输入（base64 编码图像）会让上行字节进一步偏离 token 估算
- **下行（output → SSE stream）**：每 token 还需附加 SSE 帧头、`data:` 前缀、双换行，膨胀约 4–6×；流式逐 token 发送让 TCP/HTTP/2 帧开销均摊较高

**校正后的结论**：原稿"token 比 ≈ 字节比"是**未实测假设（L4）**——具体编码层放大系数未做完整 PCAP 测量。本报告所有涉及"流量""带宽"字节量级的推算均建立在此假设之上，**任何把 162:1 直接当作字节比的引用都属误读**。完整字节级测量需要代理抓包，列为后续工作（[5A.6](#5a6-未尽事项与后续实测设计)）。**但 cache_read 本身的"是否传输"问题已经在 5A.4.1 通过 L2 文献证据闭环。**

## 5A.5 与业界估算的对照

公开数据极少，可对照的有：

| 来源 | 数据 | 与本研究对比 |
|---|---|---|
| Anthropic 公开计费文档 | input token 单价为 output 的 1/5（Opus）/ 1/4（Sonnet） | 仅说明 input 量被预期为远大于 output，无具体比例 |
| OpenAI 公开计费 | input/output 单价比约 1/4–1/5 | 同上 |
| a16z《The Economics of Generative AI》(2024) | 提到典型 LLM workload input:output 在 10:1–30:1 | **本研究测得 162:1，高出 5–16 倍** |
| SemiAnalysis 推理成本拆解 | 默认假设 input:output ≈ 20:1 用于成本建模 | 同上 |

**差距的口径警示**：a16z / SemiAnalysis 的估算多面向"chatbot 对话型"workload，**且不一定区分 cache_read 与 input token 的统计口径**。本研究覆盖的是 Claude Code 类**重型 Agent**，每轮有完整文件读取、工具结果回灌、对话历史重传。在**同一口径下**对比的话，Agent workload 的 input:output 比例的确显著高于 chatbot；但**直接说"业界系统性低估 5–16 倍"是口径混用的过强表述**——业界假设是否包含 cache_read、是否按 usage token 还是网络字节都不明，单一比例直除不能得出系统性低估结论。

**校正后的表述**：本研究单用户样本的 Claude Code Agent 比例（162:1）显著高于若干 chatbot 时代公开成本模型采用的假设（10:1–30:1），暗示 chatbot 时代假设**可能不适用于** Agent workload，但具体偏离量级需在同口径下做跨厂商、跨用户的扩样验证。该论断作为开放假设 H5 保留至 [Part 7.3](../07-evidence/07-evidence.md#假设-h5业界-10130-估算系统性低估-agent)。

## 5A.6 未尽事项与后续实测设计

本节实测有四项已知局限，列为后续工作：

1. **单用户样本，无法做跨用户分布**：需要采集 10+ 用户、跨多种 workload（编码 / 浏览器 / RAG / 多模态）的同结构数据。可通过 Claude Code 的 OpenTelemetry 导出接口收集匿名指标。
2. **token 比不等于字节比**：需要代理层抓包（mitmproxy + 受控 CA）实测 HTTP 请求/响应体的真实字节，建立 token→字节的放大表。
3. **未覆盖多模态调用**：本数据集中视觉、PDF、音频调用比例 < 1%。需补充 Computer Use / Browser Use 场景的专项采样。
4. **未做时间序列**：未量化"上行峰值是否与下行峰值同步"。这是 95th percentile 计费失真分析的关键。需按 1 分钟粒度对齐时间戳后再分析。

下一版数据采集脚本应输出每次调用的：
- timestamp
- request body 字节数（HTTP 层实测）
- response body 字节数（HTTP 层实测）
- TLS 帧数与每帧字节
- workload 类型标签

实测脚本设计草案见 [`empirical-protocol-v2.md`](empirical-protocol-v2.md)（待写）。

## 5A.7 本节小结

**已实测（L1），可作为后续推理基础**：

- Claude Code 编码型 Agent 在单用户重度使用场景下：**上行 / 下行 usage token = 162 : 1（全体加权），中位数 386 : 1**
- 上行 usage token 中 **96.1% 计入 prompt cache_read 字段**（计费层的 1/10 折扣已实测）
- 模型尺寸越小、用作"流水线节点"的角色越多，比例越极端（Haiku 281:1）
- workload 类型对比例影响巨大（纯对话 14:1 vs 多 Agent 编排 228:1）

**已确证（L2，新增）**：

- **prompt caching 不削减客户端→服务端 HTTP 字节**——只削减计费与服务端 prefill 计算（[H6-文献证据](H6-文献证据.md)）。Anthropic 服务端通过 cumulative prefix hashing 识别缓存匹配，要求客户端完整提交内容。**这把"96.1% cache_read 对应的字节实际仍在上行链路"从假设升级为已确证。**

**已推断（L3-L4）**：

- token 比 ≈ 字节比 仅是未实测假设（编码层放大系数），不能直接外推到网络字节
- 公开业界估算（10:1–30:1）面向 chatbot 假设，与 Agent 实测有显著差异，但口径不同不能直接得出"系统性低估"

**待验证（开放假设，留至 Part 7）**：

- 跨用户、跨厂商、跨工具栈的真实 usage token 分布
- HTTP 层网络字节比（须抓包测量编码层放大系数）
- ~~prompt caching 是否真的不削减字节（H6）~~ **已通过文献证据解决，见 [H6-文献证据](H6-文献证据.md)**
- 上行峰值与下行峰值的时间同步性
- 多模态 Agent 上的具体放大倍数
